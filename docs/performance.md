# 流畅度：实际经过、有效改动与失败路线

## 先区分三个现象

最初是“本来约一秒的动画拖成两秒”；部分修改后，用户反馈动画时长基本恢复，但仍丢帧；另外还有画面偏移、重影或残留。第三项用户说明早就存在，要求先专注流畅，因此没有把几何问题一并认定为新补丁造成，也没有宣称已修好。

普通等应用加载完成再返回，不能代表刚点开约0.1—0.35秒就上滑、立刻点下一个应用。后者包含启动窗口、桌面返回动画、系统窗口和新应用初始化的重叠。

## 从GPU假设转向窗口路径

早期一些GPU指标较好，但用户仍反馈很卡。回看输入事件发现，某组对照从11/12次图标抬手到达桌面变为7/12，部分事件落进前一个应用；B站resume数量也减少。这种对照做的工作变少，不能从更低GPU等待推导“完整12次切换更流畅”。

随后细采样记录到：WMShell主线程一帧约241ms，窗口relayout约109ms但大部分时间在等待；桌面的RecentTasks Binder查询可等约300ms。AMS/WMS全局Java监视器、窗口回收及其他进程退出链路都能出现在关键路径上，不能统一解释成GPU算力不够。

这些是特定帧的路径证据。后续也同时看到RenderThread在dequeueBuffer睡眠，和SystemUI线程长时间Runnable但拿不到CPU，两者需要分开处理。

## 最终保留：辅助触摸窗口的生命周期

定位到SystemUI的 `FullscreenCaptionHandleViewHolder`。其 `StatusBar InputLayer of Task=…` 是全屏窗口标题/分屏入口相关的辅助输入层，第一次addView/relayout会进入窗口管理路径。一个历史120Hz样本中，SystemUI约294ms的一帧包含约255ms首次relayout。

原代码保留了输入token回退路径，因此可以改创建时机，而不直接删掉功能：

1. 原本立即创建改成View的400ms延迟任务。
2. 新位置和尺寸先保存；取消、隐藏或销毁时撤销待执行任务。
3. v2再检查TaskInfo是否仍有焦点，失焦时取消尚未创建的层。
4. 已存在的窗口仍遵循原拖动生命周期；不把所有辅助窗口强制销毁。

用户先确认日常改善，再确认连续打断好很多。一次历史快速样本中，辅助窗口创建由4次减到2次，最大创建耗时由约119.48ms变成44.82ms；这不是恒定收益比例，各轮工作量和应用状态并不完全相同。

当前源：[延后创建](../patches/work/patch_caption_defer.py)、[失焦取消](../patches/work/patch_caption_focus.py)。最终已直接合入SystemUI，不再依赖试验模块启动。

## 最终保留：关闭自动分屏推荐

`SplitRemindView` 会加载两个应用图标、建立新窗口并绘制推荐。一次约209.95ms的SystemUI长帧包含约80.23ms relayout和56.26ms draw。服务端实际观察的设置键是 `Settings.System.recommender_split_screen_enable`。

将其置0后，目标样本里SplitRemindView的trace/draw消失，用户反馈有改善但仍卡。关闭的是自动推荐，不是手动分屏或平行视窗。这个设置随v23首启默认值交付。

## 未保留的试验

| 路线 | 得到什么证据 | 最终决定 |
|---|---|---|
| GPU调频队列优先级、AS1、额外GPU最低频 | 部分局部指标好看，用户反馈变差；另有输入覆盖问题 | 撤回，不能作为当前推荐 |
| 近期SF latch、zram lz4组合 | 整组回退后严重卡顿仍在 | 撤回这组试验；不能推断所有老功能都该删 |
| 停旧前台调度 | 单独停用也未消除卡顿 | 恢复原有基线；v23保留原调度交付，不新增本轮策略 |
| Nirvana LiteNoSwap临时关闭 | 一次批量AppDeath锁占用消失，窗口等待与卡顿仍在 | 原状态恢复，不作为解决方案 |
| 框架锁boost兼容与平衡修正 | 代码确有门槛/配对问题，部分帧变好，WMShell尾部反而更差；用户仍卡 | 补丁撤回，源码问题不等于整体性能收益成立 |
| 144→120Hz | 一组A/B/A里CPU空闲和普通帧间隔改善，但极快打断仍停顿；用户两种都卡 | 恢复144Hz，不以降规格作为最终改善 |
| SystemUI/RenderThread提高nice优先级 | 单个等待下降，整段返回帧尾没有稳定改善 | 恢复原值，没有保留常驻优先级脚本 |
| 七条关键线程绑定大核 | 动画线程自身P95下降，SF合成节奏P95由约14ms变为20.87ms，回退恢复约14.33ms | 撤回；多核优化不能只看某线程跑得快 |
| 回收线程绑核 | A/B/A的>50ms间隔数量4/5/4，无稳定收益 | 撤回 |
| 400→800ms延后 | 辅助层更少，整段合成节奏没有稳定收益 | 恢复400ms |
| recents-v3取消待创建层 | 目标取消trace未出现，无法建立收益 | 恢复v2 |
| TO_BACK-v4取消路径 | 实际走到5次、取消1次，仍有长relayout；工作量也不同 | 恢复v2，不因路径能执行就保留 |
| 延后ART后台collector切换 | collector工作减少，整段帧指标混合，部分启动代理覆盖不等 | 原ART恢复，未改原生容器 |
| 桌面完整手势队列重放 | 目标replay日志为0，无因果增益 | 原Launcher恢复 |
| 强制client合成 | 一组HWC CPU从约2509ms降到620ms，但GPU/帧耗时变差 | 恢复原合成标志 |
| 特定应用后台线程降优先级 | 应用阶段负载变化大，无稳定系统收益 | 没有留下按应用名单优化 |

“未保留”也包括证据不足的情况，不等于所有设备上理论都无效。研究补丁在[research](../research/README.md)，不参加默认构建。

## 两个有数值的反例

GC延后在轻量、启动后稳定的A/B/A中，快速样本的native missedFrames分别为A1 93/82、B1 165/132、A2 92/129；present间隔P95桶分别14/13、13/13、20/13ms。它没有形成一致的整段收益。

强制client合成的两个快速样本，frame-duration P95桶为A1 7/8ms、B1 13/13ms、A2 8/7ms。减少HWC CPU本身不是最终目标。完整阶段与温度原始读数见[数据目录](evidence/README.md)，不能把各阶段当恒温实验。

## 当前结论

保留用户确认有效的窗口生命周期改动和原生规则，恢复原ART/Launcher及未获益的临时优先级/绑核/合成设置。最终同一组代码得到“日常和连续打断都正常，可以用”的反馈，最终完整包又做了实际双清、首启和重启检查。少量掉帧仍存在，没有证据证明已经触及硬件上限。
