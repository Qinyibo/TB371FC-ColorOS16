# 相机：文件可解码与录像合格是两回事

## 从附带APK到系统默认相机

早期只是包里附带ZUI APK，并不保证双清后有系统默认相机。v22b加入同签名系统基座与首启完整包恢复，移除旧Open Camera；实际检查SYSTEM/UPDATED_SYSTEM_APP及拍照/录像Intent解析。普通侧装能打开，不能替代系统默认相机角色测试。

## v7修复完成回调

限时录像时，底层完成回调可能早于应用自己的停止标志。旧 `MediaRecorderWrapper.onInfo` 用mStopping判断，误把正常OK/EOS当编码错误。

v7仅改该判断，保留onError和isEncodeSuccess，没有强制返回成功。普通调用方UID下，默认拍照返回有效JPEG、默认录像返回调用方，音视频轨和画面可解码；Camera1/Camera2前后摄JPEG与720p YUV也有软件测试。

源码：[build_camera_completion_v7.py](../camera/build_camera_completion_v7.py)。本次最终v23使用v7，APK SHA256：

```
0c72c201cef16bb4e187257690d7963b3c49c13dfa990ebb3cc1b53da57e7b7e
```

## v8是历史现场试验，不是当前包

此前前摄HIGH请求选到4K，8秒只有26帧，另一个3秒样本仅1帧；1080p对照8秒约171帧。v8只对spinel/SDK36/摄像头1的默认HIGH且有1080p配置时选1080p，显式2160p和后摄路径不改。历史样本约8秒190帧，音视频时长约8.00/8.02秒。

这说明限定请求路径的候选值得继续验收，不能证明前摄硬件“不支持4K”，也不能把当时装到设备上的v8写成封存ZIP已经含v8。最终重新确认当前安装与v23都为v7，避免同versionCode或旧说明造成混淆。

## 仍开放的质量问题

后摄一个8秒样本只有48帧，视频轨7.66秒而音轨8.03秒。文件存在、可解码、编码器是硬件AVC，并不能说明帧率或同步质量合格。曝光、处理链等待与配置选择仍需进一步区分。

用户曾确认一次花屏仅在相机画面，时间邻近前摄HIGH试验；没有证据把它与系统偶发黑屏归为同一根因。所有扫码、视频通话、前摄显式4K、高级拍摄模式都没有完成普遍验收。

继续工作应固定摄像头、请求质量、实际选中尺寸、录制时长、帧数、视频/音轨时长与解码结果，分别比较。测试图片/视频没有公开，仓库保留修正源码和数值经过。
