# 怎样复现与衡量连续打断

## 固定行为，而不是只固定脚本次数

本项目常用微信、QQ、B站、抖音四个原版应用。普通流程约打开3.5秒再上滑返回；快速流程包含约0.22秒停留、120ms上滑、约0.44秒返回后再点下一项；更快的历史压力流程曾用0.08秒停留、80ms上滑和0.12秒返回。实际事件间隔还包含input命令及系统处理开销，这些sleep不是物理输入的精确时间戳。

三轮四应用意味着12次打开尝试、12次返回阶段，不自动等于12次成功启动。对照应同时看图标输入目标、窗口/任务变化、内容是否真出现，以及用户手感。直接 `am start -W` 可用于冷启动诊断，不能替代桌面点击的快速打断。

每轮记录旋转、分辨率、字体/密度、刷新率、温度、内存、进程冷暖状态和实际加载文件。A/B/A或A/B/B/A有助于识别一次性预热，但并不能保证温度、缓存和应用网络内容完全相同。

## 本项目踩过的指标陷阱

| 容易得出的结论 | 实际需要核对 |
|---|---|
| 脚本完成12次，所以12个应用都打开了 | 快速触点可能落进旧应用；也可能启动被取消、延后或只是TO_FRONT |
| 没有performResume，所以启动失败 | 某些采样配置不记录该标记；复用前台任务也可能没有同样路径 |
| 桌面dispatchInputEvent收到UP，所以图标点到了 | 桌面还有全局上滑观察通道，不能与真实桌面窗口事件混为一谈 |
| FrameTimeline相邻帧差80ms，所以全屏冻住80ms | 中间可能仍有其他合成；必须核对实际composite/present与相应layer |
| TimeStats最大present间隔就是卡顿 | 统计包含应用停留、空闲和排空阶段，长间隔可能没有待显示的新帧 |
| RenderThread睡眠就是CPU不够 | dequeueBuffer、Binder、监视器等待与Runnable抢不到CPU是不同问题 |
| HWC CPU下降就是更流畅 | 强制client实验反而增加GPU合成和帧尾成本 |
| kswapd占用高，所以换zram压缩算法 | 一个联合采样里回收占36.39%，LZO压缩只1.99%，主要还含页引用遍历 |
| 一次无崩溃就是黑屏修好 | 偶发问题需要故障现场；有限测试只能说明该窗口未复现 |

## 采样开销与完整性

先用低开销的FrameTimeline、进程信息及少量输入/阶段标记看端点；需要解释某个等待再加sched、Binder、dalvik或view/wm。此供体里gfx也可能带出大量view记录，不能以为删掉view类别就一定很轻。

历史曾出现16MB/64MB环形缓冲覆盖早期阶段，进程名/阶段丢失。那些对照不纳入结论。除严重性为error/data_loss的统计外，也查chunk overwritten计数；不只看命令返回0。普通流程应保留8个阶段，三轮快速流程保留24个完整阶段。

录屏用于识别画面偏移、残留或明显跳变。编码器会增加负载，其帧间隙不能直接替代物理显示的帧间隔。无有效输入的被动采样不能用来反驳用户“刚才很卡”。

标准字段含义可对照 [Perfetto FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline)。本项目数值的解释受上述现场限制，不是通用跑分排名。

## 可复用材料

[research/measurement](../research/measurement/) 提供最终阶段标记夹具、轻量配置和SQL。坐标依赖当时桌面布局，不是通用自动化安装器；先核对当前图标和旋转，再使用。夹具通过参数限制轮数、有结束清理，不包含常驻性能策略。

一个最小复核顺序是：保持正常动画与平行视窗，先手测普通与快速操作；再做一次短采样确认核心进程未变、trace覆盖完整，最后将结果交回用户。只有出现新失败再补定向检查，避免无限扩大工具链。

## v23最后一次短采样怎样读

同一组最终运行代码的12次打开/返回采样，24阶段完整，核心进程保持稳定。用于统计的后两轮区间中，SurfaceFlinger记录965帧、11个Dropped Frame，latency P95约13.04ms，最大26.01ms；Launcher记录3269条、3个Dropped Frame，latency P95约18.91ms、最大82.75ms。

各进程统计可能包含多layer及不同帧标记，不能加总成全屏FPS或“丢帧率”。该采样没有证明四应用每次都产生相同可见内容；用户的实际操作反馈是另一份证据。完整查询输出见[release-interruption-metrics.txt](evidence/release-interruption-metrics.txt)。最终ZIP后来又双清验证首启与重启，没有在第二次双清后假装重做同一份四应用登录场景。
